# 0005. Раздельная маршрутизация прокси по стадиям + ретрай бот-гейта ротацией IP

- **Статус:** Accepted
- **Дата:** 2026-07-30
- **Контекст-крейты:** `core` (config), `ytdlp`, `pipeline`; уточняет ADR-0004

## Контекст

Живой прогон на Arch-сервере уперся в YouTube-бот-гейт («Sign in to confirm
you're not a bot») **несмотря на рабочий PO-токен**. Диагностика показала:
вызов пайплайна (`yt-dlp -J`) байт-в-байт совпадает с ручным тестом, который
проходит. Значит бага в конфиге/бинаре нет — гейт срабатывает **по объёму**:
одиночный `-J` проходит, но `meta_workers = 4` подряд по всему списку сидов с
**одного серверного IP** триггерят стену на N-м запросе.

Ключевой вывод: **PO-токен доказывает origin, но не отмывает репутацию IP.**
Он не спасает серверный/датацентр-IP от гейта под нагрузкой. Рычаги против
этого — либо куки (нежелательно: риск бана реального аккаунта; burner — костыль),
либо **чистые IP из пула** (residential).

Но residential тарифицируется по трафику ($/ГБ). Метаданные (`-J`) — килобайты,
через residential почти бесплатны. А **скачивание видео — гигабайты**: гнать его
через residential разорительно. Значит нужен разный маршрут для лёгкой стадии
(метаданные) и тяжёлой (медиа).

Плюс два дефекта текущего поведения:
1. Бот-гейт классифицировался как `Error::Tool` — **не retryable**, т.е. каждое
   пойманное видео терялось навсегда, хотя при пуле прокси повтор с другого IP
   прошёл бы.
2. Ретраи временных ошибок шли синхронно у всех воркеров (фикс. `1<<attempt` c)
   — лёгкий thundering-herd.

## Решение

1. **Раздельные пулы прокси по стадиям** (`[proxy]` + опц. `[proxy.media]`):
   - `[proxy]` — основной пул: discovery + метаданные (+ нативный TikTok). Сюда
     ставят чистый residential (запросы лёгкие).
   - `[proxy.media]` — отдельный маршрут скачивания:
     - отсутствует → медиа идёт через основной пул (**обратная совместимость**);
     - `direct = true` → медиа качается **напрямую**, мимо дорогого пула;
     - `file = "…"` → свой (дешёвый датацентр) пул под гигабайты.
   - `YtDlp` держит два пула: `meta_proxy` (для `-J`/`--flat-playlist`) и
     `media_proxy` (для скачивания). `run()` принимает пул явным аргументом.

2. **Бот-гейт становится retryable при наличии пула.** `classify()` теперь
   метод: если пул есть — гейт → `Error::Transient` (помечает текущий IP плохим →
   cooldown+ротация в пуле, следующая попытка уходит на свежий IP). Если пула
   нет — остаётся терминальной `Error::Tool` с подсказкой (residential/куки),
   т.к. повтор с того же IP бесполезен.

3. **Экспоненциальный backoff + джиттер** в `retry()`: задержка `1,2,4,…,30` c
   плюс джиттер до +25% (xorshift по атомарному счётчику — без часов и без
   `rand`, чтобы не тащить зависимость и не ломать clock-free-стиль). Джиттер
   рассинхронизирует воркеры.

## Последствия

- Рекомендуемый профиль YouTube: `[proxy]` = rotating residential под
  метаданные, `[proxy.media] direct = true` (или датацентр-пул) под скачивание;
  PO-токен оставляем. Это реверсит «YouTube строго direct» из рабочих заметок к
  ADR-0004 — маршрут теперь конфигурируемый, а не захардкоженный.
- **Метаданные-first дешевле всего и не требует кода:** `[media] download = false`
  (или просто не запускать стадию `media`) — по ADR-0004 все 9 ML-полей приходят
  из `-J`, медиа для ML-датасета не обязательно.
- Гейтнутые видео больше не теряются безвозвратно при наличии пула — ротация +
  backoff дают им 2 повтора на свежих IP.
- Обратная совместимость полная: старые конфиги без `[proxy.media]` ведут себя
  как раньше (медиа через основной пул или напрямую, если пула нет).

## Альтернативы

- **Burner-аккаунт куки вместо residential.** Работает, но: аккаунт может уйти в
  бан, куки протухают и требуют ручного обновления, `cookies_from_browser` не
  живёт на headless-сервере. Оставлено как запасной путь (подсказка в
  терминальной ветке `classify`), не как основной.
- **Один пул на все стадии.** Отвергнуто: жжёт дорогой residential-трафик на
  гигабайтах видео без всякой пользы (CDN googlevideo гейтит слабее player-запроса).
- **Гейт всегда retryable (даже без пула).** Отвергнуто: без пула повтор идёт с
  того же IP → бессмысленная задержка; терминальная ошибка с подсказкой честнее.

## Открытые вопросы

1. Тот же объёмный замер (open question ADR-0004 №1), но уже на residential:
   при каком RPS/объёме на IP начинается гейт — калибрует размер пула.
2. Нужен ли `[proxy.media]` отдельный rate-limit (сейчас `requests_per_sec`
   общий на платформу, не на пул).
