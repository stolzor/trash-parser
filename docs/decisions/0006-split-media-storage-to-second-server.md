# 0006. Медиа-хранилище выносим на второй сервер (раздельные MinIO)

- **Статус:** Accepted
- **Дата:** 2026-08-19
- **Контекст-крейты:** `pipeline`, `store-s3`, `cli`; уточняет ADR-0005

## Контекст

Сервер A (где идёт сбор, крутятся MinIO+Postgres) имеет всего ~139 ГБ свободного
места. Метаданные (raw/meta, нормализованное) — мелочь (килобайты/видео), но
**медиа — гигабайты** и на A не влезет. Сервер B в той же LAN имеет 500+ ГБ и
предназначен под медиа.

Ключевое свойство кода (проверено): media-стадия (`pipeline::fetch_media`)
читает задания **из манифеста (Postgres)** — `claim_media_batch` отдаёт
video/url/domain/duration — и пишет **только** `store.put_media(...)`. Метаданные
она не читает из стора и не перезаписывает. Значит стор media-стадии можно
направить в другой MinIO, не затрагивая метаданные.

Ограничение: у пайплайна **один storage-backend на запуск**. Поэтому нельзя в
одном прогоне писать мету в MinIO A, а медиа — в MinIO B.

## Решение

**Раздельные MinIO + раздельные стадии** (Вариант 1):

1. **Сбор метаданных** (discover/harvest, `config/seeds.youtube.toml`) — как есть,
   стор = MinIO на A. Идёт по таймеру (ADR-0005 / deploy/).
2. **Media-стадия** — отдельный конфиг `config/seeds.media.toml`, где
   `[storage.s3] endpoint` смотрит на **MinIO сервера B** (`http://B:9000`,
   бакет `detox-media`). Запуск: `detox-parser media --config …` (только
   `fetch_media`, без discovery). Медиа льётся на B, метаданные остаются на A.
3. **Манифест общий** (Postgres на A) — связывает обе стадии; `media_path` в
   манифесте указывает на ключ в MinIO B.
4. MinIO на B поднимается своим compose — `deploy/docker-compose.media.yml`
   (только MinIO + бакет), порты на 0.0.0.0 для доступа A по LAN.

Формат медиа по умолчанию — `≤360p` (`worst[height<=360]…`), long — окнами
(`long_windows`), чтобы вписаться в бюджет диска B. Точную оценку объёма даёт
`scripts/estimate_media.py` / `make media-estimate` (разбивка short/long)
ПЕРЕД включением скачивания.

## Последствия

- Медиа изолировано на B; A не переполняется. Метаданные и медиа честно разнесены
  по машинам — соответствует медальону (Bronze-мета vs медиа-артефакты).
- `export` (parquet из normalized) работает на A как раньше — он про метаданные.
- Цена: две инсталляции MinIO и ручной запуск media-стадии отдельной командой
  (не в общем таймере). Приемлемо: скачивание медиа — редкий тяжёлый батч, а не
  постоянный поток.
- staging-буфер медиа временно живёт на A (файл удаляется после заливки на B) —
  пиковая нагрузка на диск A ограничена `media_workers` × размер файла, не суммой.

## Альтернативы

- **Media-стадию целиком запускать на B** (Вариант 2): B тянет манифест A по LAN,
  качает локально. Чище по нагрузке, но требует Rust+yt-dlp+ffmpeg на B и
  сетевой доступ к БД. Отложено — можно перейти без изменений кода (тот же
  `media`-конфиг, только запуск с B и endpoint = localhost).
- **FS-backend на смонтированный диск B** (NFS/sshfs, Вариант 3): без второго
  MinIO, но staging/запись идут файловыми операциями по сети — медленнее и
  хрупче S3. Отвергнуто.
- **Один общий MinIO на B под всё** (и мету, и медиа): мета уже на A, переезд
  ломает текущий сбор; смысла нет — мета мелкая.

## Открытые вопросы

1. Порог перехода на Вариант 2 (media на B), если LAN-заливка A→B станет узким
   местом при большом объёме.
2. Нужен ли systemd-таймер и для media-стадии, или ручной батч достаточен.
