# 0004. Проверка области: yt-dlp покрывает VOD → тяжёлые сессии отложить

- **Статус:** Accepted
- **Дата:** 2026-06-26
- **Контекст-крейты:** `session`, `tiktok`, `ytdlp`; уточняет ADR-0002, ADR-0003

## Контекст

ADR-0002 (прогретые сессии) и ADR-0003 (JS-фингерпринт) — тяжёлая
анти-детект-инфраструктура. Прежде чем строить браузерный warmer / TLS-клиент,
проверили гипотезу области (open question ADR-0003 №1): **достаточно ли SSR +
yt-dlp для сбора VOD-метаданных без подписанных XHR?**

## Измерения (live, 2026-06-26)

Проба прямо с **датацентр-IP, без прокси и без кук**, yt-dlp 2026.06.09:

| Проверка | Результат |
|---|---|
| Достижимость TikTok | ✅ дотянулся даже с датацентр-IP |
| Покрытие 9 ML-полей (`-J` на видео) | ✅ id, view/like/comment/repost_count, duration, upload_date, timestamp, channel, track, title, description |
| Пробел покрытия | `channel_follower_count` = None (единственный) |
| Глубина (`--flat-playlist --playlist-end 50`) | ✅ 50/50 уникальных — паджинирует далеко за первую SSR-порцию |

Объёмный прогон harness'ом (100 видео, датацентр-IP, без прокси/кук, пауза 250мс):

| Метрика | Результат |
|---|---|
| yt-dlp success | 97/100 (3 отказа = `unavailable`, контентная убыль, не стена) |
| success-rate по окнам | 100/100/90/95/100 — **тренда вниз нет** |
| нативный per-video `fetch_page` | 100/100 |
| покрытие 9 ML-полей | 100% |
| нативный discovery листинга | 2 items (бот-стена страницы) — слабое звено, перекрыт yt-dlp |

Признаков деградации IP под нагрузкой на этом масштабе нет — приоритет сессий
падает ещё ниже. Остаётся проверить тот же прогон на residential и на бóльшем
объёме (open question №1).

## Решение

1. **L4-подписи не нужны** для сбора VOD — подтверждено. yt-dlp закрывает и
   покрытие полей, и глубину. ADR-0003 п.3 переходит из гипотезы в факт.
2. **Тяжёлые части сессий откладываем** (`BrowserWarmer`, TLS-impersonation-клиент,
   каталог fingerprint). Их единственное оставшееся оправдание — **удержание
   success-rate на большом объёме**, а это вопрос масштаба, а не возможности.
   Строим их только при сигнале деградации на целевом объёме.
3. **Clock-free ядро `session` оставляем** как есть — оно дёшево, оттестировано
   и готово, если объёмный тест покажет необходимость. Ничего не выкидываем.
4. **Следующий гейт — объёмный тест** на residential-прокси: устойчивость
   success-rate на сотнях/тысячах запросов во времени. Только его провал
   разблокирует постройку браузерного слоя. Harness готов:
   `crates/tiktok/examples/volume_probe.rs` (success-rate по окнам, разбивка
   отказов, покрытие полей; нативный путь vs yt-dlp).

## Последствия

- Экономим недели на браузерной/stealth-инфраструктуре, пока нет доказанной
  нужды. yt-dlp остаётся рабочей лошадью VOD (как и зафиксировано в
  `architecture.md`).
- Приоритет смещается обратно на дешёвые улучшения нативного пути (Шаги 2–4) и на
  объёмный замер, а не на анти-детект.
- `channel_follower_count` — единственный пробел поля; закрывается отдельным
  fetch'ем метаданных канала (не требует сессий).

## Альтернативы

- **Строить warmer/браузер сразу** (как подразумевал 0002). Отвергнуто: измерение
  показало, что возможность уже есть без него — это была бы оптимизация вслепую.
- **Портировать подписи в Rust** (ADR-0003 альт.). Тем более не нужно.

## Открытые вопросы

1. Объёмный тест: при каком RPS/суммарном объёме на один sticky-IP начинается
   бот-стена? Это калибрует, нужны ли вообще прогретые сессии.
2. Источник `channel_follower_count` (отдельный extractor канала).
