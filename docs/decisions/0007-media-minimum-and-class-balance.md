# 0007. Минимум медиа-данных и баланс классов (short/long)

- **Статус:** Accepted
- **Дата:** 2026-08-19
- **Контекст-крейты:** `pipeline` (media/quota), конфиги; уточняет ADR-0006

## Контекст

Собрано ~62k видео (raw meta). Оценка объёма (`scripts/estimate_media.py`):

| Домен | Видео | Длит. | Целиком 240p | Целиком 360p |
|---|---|---|---|---|
| short (≤90с) | 4153 | 59 ч | ~4.5 ГБ | ~8.8 ГБ |
| long (>90с) | 57618 | 33705 ч | ~2293 ГБ | ~4147 ГБ |

Скачивать long целиком нереально (терабайты) и не нужно. Два вопроса: **сколько
медиа реально нужно на видео** и **в какой пропорции классов**.

## Анализ

**Признаки — потоковые** (темп монтажа, оптический поток, насыщенность/яркость,
громкость/темп аудио). Они не требуют высокого разрешения и полного ролика:

- **short** — короткий, стимуляция однородна, сэмплировать нечего → берём
  **целиком**, но в **240p** (потоковым признакам хватает). Дёшево.
- **long** — стиль **стационарен** (лекция остаётся лекцией, быстрый монтаж —
  быстрым), характер ловится **несколькими окнами**. Минимум — **3×20с**
  (начало/середина/конец, устойчиво к интро/аутро) в 240p. Полная аудио-дорожка
  для long НЕ дешёвая (терабайты) → именно окна.

**Баланс классов.** short (4153) — миноритарный класс и **потолок**
сбалансированной выборки (long завались, 57k). Наращивать long, пока short мало,
бесполезно — модель упрётся в 4153. Для потоковых признаков + классической
модели тысячи примеров/класс рабочи, но 4153 — нижняя граница качества.

## Решение

1. **Разрешение — 240p** (`worst[height<=240]…`). 360p только если добавятся
   признаки лиц/экранного текста.
2. **short — целиком**, все доступные (квота не лимитирует, они дёшевы).
3. **long — окнами 3×20с** (`long_windows=3`, `long_window_seconds=20`).
4. **Баланс 1:1**: квота `long` = числу собранных short на момент скачивания
   (сейчас плейсхолдер 4200 ≈ текущему short). Выравнивать перед `media-run`.
5. **Рост минорного класса — приоритет над скачиванием медиа.** Добавлены ~12
   разнообразных short-сидов (pets/magic/makeup/sports/meme/recipe/diy/comedy/
   gaming/try-not-to-laugh/science/#shortsfeed). Таймер копит short; медиа качаем
   когда short подрос. Пропорция сидов теперь short-тяжёлая осознанно.

Реальный бюджет (оценка [B] с окнами, 240p): short целиком + long 3×20с при
балансе 1:1 ≈ **десятки ГБ** — вписывается в 500 ГБ B с огромным запасом.

## Последствия

- Датасет растёт по минорному классу (short), потолок качества поднимается.
- Медиа-объём мал → скачивание быстрое, диск B не риск.
- Оценщик `estimate_media.py` теперь показывает блок [B] (с учётом окон) —
  планирование по реальной стратегии, а не по «целиком».
- Отложено: TikTok (огромный источник short) — по решению пользователя не
  подключаем сейчас; когда встанет residential, это главный рычаг роста short.

## Альтернативы

- **Качать все 57k long.** Отвергнуто: дисбаланс 14:1 вредит модели, диск и время
  впустую. Больше данных ≠ лучше при перекосе.
- **360p/полное видео.** Не нужно под потоковые признаки; ×2+ места без выигрыша.
- **Полная аудио-дорожка для long вместо окон.** Терабайты — дороже видео-окон.

## Открытые вопросы

1. Целевой размер short (8к? 15к?) — определяет, сколько сидов/времени и нужен
   ли форсаж residential+TikTok.
2. Достаточно ли 3×20с окон для «быстромонтажных» long (видеоэссе) — проверить
   на baseline-модели, при нужде поднять `long_windows`.
