# 0002. Подсистема прогретых сессий (`crates/session`)

- **Статус:** Proposed
- **Дата:** 2026-06-26
- **Контекст-крейты:** новый `session`; затрагивает `tiktok`, `pipeline`,
  `core` (proxy), `ytdlp`
- **Уточнено:** [ADR-0004](0004-area-check-ytdlp-covers-vod.md) — проверка области
  показала, что yt-dlp покрывает VOD; тяжёлые части (browser warmer / TLS-клиент)
  отложены до объёмного теста. Clock-free ядро остаётся.

## Контекст

TikTok скорит **сессию/устройство**, а не отдельный запрос. Холодный запрос с
датацентр-фингерпринтом и свежим (или отсутствующим) `msToken` получает бот-стену
или капчу гораздо чаще, чем «прожитая» сессия с историей. Шаги 1–2 (классификация
отказов + бутстрап `ttwid`) снижают долю стен, но **не меняют потолок**:
фундаментальные гейты — `msToken` (генерится JS), подписи XHR, device-fingerprint
и **TLS/HTTP2-отпечаток (JA3/JA4)** — остаются.

Главный архитектурный конфликт с тем, что есть: `core::ProxyPool::acquire()` —
это round-robin **без привязки идентичности**, каждый вызов отдаёт другой прокси.
Прогрев же требует обратного — **стабильной связки `IP ↔ fingerprint ↔ cookies`**,
переиспользуемой во времени. Нельзя прогреть IP, на который не можешь вернуться.

Цель проекта — собрать VOD-метаданные для ML-датасета (Bronze-контракт, см.
`docs/architecture.md`). Подсистема сессий — это **рычаг надёжности сбора**, она
не должна протекать в Bronze-контракт.

## Решение

Ввести крейт `crates/session`, который заменяет для TikTok-пути модель «прокси на
запрос» на модель «**прогретая идентичность на запрос**». Идентичность — это
персистентная связка:

```
Identity {
  id            : уникальный
  sticky_proxy  : residential/mobile URL со стабильным exit-IP (sticky session)
  fingerprint   : { ua, accept_language, timezone, locale, tls_profile/JA3 }   // СТАБИЛЕН на всю жизнь идентичности
  cookie_jar    : { ttwid, msToken, tt_chain_token, sessionid?, ... }           // персистентный
  lifecycle     : Fresh | Warming | Ready | Cooling | Burned
  health        : created_at, last_warmed_at, req_count, consecutive_fails, score
}
```

Семь принятых решений:

1. **Единица acquire — идентичность, не прокси.** TikTok-путь берёт из
   `SessionPool` готовую (`Ready`) идентичность, использует её и репортит исход.
   `ProxyPool` остаётся как есть для YouTube/yt-dlp, где stickiness не критична.

2. **Консистентность личности — инвариант №1.** На всю жизнь идентичности
   `IP + fingerprint + cookies` остаются согласованными. Никогда не отправляем
   один cookie-jar с другого IP и не меняем TLS-профиль под фиксированным UA —
   рассогласование палит сильнее, чем холодный запрос. Это главный инвариант, под
   него подстраивается всё остальное.

3. **Гибрид «браузер минтит — лёгкий клиент реплеит».** Прогрев (генерация
   `msToken`, старение `ttwid`, немного человекоподобной навигации) делает
   **браузерный воркер** (headless Chromium через `chromiumoxide`, без Python).
   Он запускается **изредка на идентичность** (первичный прогрев + периодический
   refresh), а не на каждый запрос. Боевые запросы идёт дешёвый HTTP-клиент,
   переиспользуя cookie-jar.

4. **TLS-фингерпринт обязан совпадать с браузером.** Голый `reqwest`+rustls
   имеет не-браузерный JA3 — прогрев браузером + реплей через rustls обнуляет
   смысл. Для боевого реплея TikTok нужен клиент с браузерным TLS-отпечатком
   (см. открытый вопрос — выбор клиента).

5. **Сессии персистентны и локальны воркеру.** Прогрев дорог — выкидывать его
   между запусками расточительно (и всплеск повторного прогрева сам выглядит
   бот-подобно). Храним в **локальном SQLite** (`rusqlite`, уже в зависимостях).
   Идентичность принадлежит **одному воркеру** (тому, чей браузер её прогрел):
   шарить один cookie-jar между воркерами/IP = гарантированный burn. Поэтому
   session store локальный, а не в общем Postgres-манифесте.

6. **Жизненный цикл и здоровье на уровне идентичности.** Состояния
   `Fresh → Warming → Ready → (in use) → Cooling → Burned`. Cooling — временный
   backoff при 429 (по образцу экспоненты `ProxyPool`). Burned — ретайр по
   жёстким сигналам (капча/логин-стена после прогрева, серия 429, смена exit-IP
   под нами). Пул держит целевое число `Ready` идентичностей и фоном пополняет.

7. **Мягкая деградация.** Нет браузера / нет residential-прокси / крейт выключен
   → TikTok-путь работает как сегодня (Шаг 1–2 + yt-dlp fallback). Сессии —
   усиление, а не жёсткая зависимость.

### Форма крейта

```
crates/session/
  identity.rs     // Identity, Fingerprint, CookieJar, Lifecycle — чистые переходы и скоринг, БЕЗ часов/IO
  pool.rs         // SessionPool: acquire Ready / report исход / фоновое пополнение (эргономика как у ProxyPool)
  store.rs        // персист в SQLite (rusqlite): load/save идентичностей и jar'ов
  warmer.rs       // трейт Warmer + браузерная реализация (chromiumoxide); мокается и отключается
  client.rs       // боевой HTTP-клиент под fingerprint+jar+sticky_proxy
  fingerprint.rs  // каталог согласованных профилей (UA/JA3/locale/timezone связаны)
```

Дисциплина ядра соблюдается: вся логика жизненного цикла/скоринга — **clock-free
и IO-free** (`now` инжектится), браузер/HTTP/SQLite живут на краях за трейтами и
юнит-тестируются как `ProxyPool`.

### Точки интеграции

- `TikTokWeb` получает опциональный `SessionPool`. `fetch_page` становится:
  `lease = pool.acquire()? → client = lease.client() → … → lease.report(outcome)`.
  Нет пула → текущий `ProxyHttp`-путь.
- **Мост к yt-dlp:** идентичность умеет выгрузить свой jar в Netscape-файл
  (переиспользуем существующую cookie-машинерию) и передать тот же `sticky_proxy`
  в yt-dlp — оба слоя живут на одной прогретой личности.

## Последствия

- **Плюс:** самый высокий достижимый «пол» надёжности; нативный путь и yt-dlp
  усиливаются одной прогретой личностью; устойчивость переживает рестарты.
- **Минус/цена:** существенная новая подсистема и **постоянное обслуживание** —
  это анти-детект-инфраструктура в состоянии гонки вооружений; TikTok ей
  противодействует. Расход CPU/трафика прокси даже на простое (поддержание пула).
- **Жёсткая внешняя зависимость:** **sticky residential/mobile-прокси**. Без них
  прогрев невозможен в принципе — ротируемый-на-каждый-запрос пул не прогреть.
- **Новые тяжёлые зависимости:** headless-Chromium-драйвер и
  TLS-impersonation-клиент (см. открытые вопросы).
- **Этика/правовое:** сознательная имитация пользователей для сбора собственных
  исследовательских данных. Фиксируем осознанно, ограничиваем нагрузку, не
  трогаем приватный/залогиненный контент без необходимости.

## Альтернативы

- **Только Шаги 1–2 + residential-прокси + yt-dlp (без сессий).** Сильно дешевле
  и, возможно, достаточно. Главная причина не выбирать прямо сейчас — заявленный
  приоритет «высокий устойчивый объём». **Замер block-rate до постройки сделал бы
  это решение обоснованным, а не на веру** (см. открытые вопросы).
- **Полный Selenium/браузер на КАЖДЫЙ запрос.** Максимально консистентно, но
  10–50× дороже, флейки, тяжело headless на масштабе. Отвергнуто в пользу
  гибрида «браузер минтит — лёгкий клиент реплеит».
- **Платные scraping/CAPTCHA-API.** Надёжнее всего и без обслуживания, но $$$ и
  внешняя зависимость от вендора. Возможный запасной вариант, не основной.
- **Шарить сессии между воркерами через Postgres.** Отвергнуто: cookie-jar с двух
  IP = burn. Идентичность строго локальна воркеру.

## Открытые вопросы

Эти развилки имеют реальную цену и выносятся в отдельные ADR при принятии:

1. **Боевой TLS-клиент.** Варианты: (а) `rquest`/`reqwest-impersonate` —
   браузерный JA3, но это форк reqwest с риском поддержки; (б) `curl-impersonate`
   через FFI; (в) гонять боевые запросы **тоже через браузер** (макс.
   консистентность, макс. цена). Нужен прототип-замер.
2. **Драйвер браузера.** `chromiumoxide` (чистый Rust, CDP) против внешнего
   Playwright-процесса. Уклон в `chromiumoxide` — без Python в Rust-пайплайне.
3. **Stealth-уровень.** Нужны ли патчи против `navigator.webdriver`/CDP-артефактов
   уже на этапе прогрева (вероятно да), и какой ценой поддержки.
4. **Объём прогрева.** Минимальная человекоподобная навигация (главная → скролл →
   видео → idle, с джиттером) против более глубокой эмуляции — компромисс
   польза/стоимость, калибруется замером.
5. **Сначала замерить.** Рекомендуется до полной постройки снять реальный
   block-rate на «sticky residential + одна прогретая руками кука + yt-dlp». Если
   успех уже высок — подсистему можно отложить.
